## Findings that belong to V6-20

1. **The retention scheduler enqueued nothing — found and fixed.** `worker.enqueue_due_retention` (`worker.py:506`) called `enqueue_job({...})` without `await`, and `enqueue_job` is a coroutine (`services/redis.py:152`): the call produced a never-awaited coroutine, pushed nothing, and `retention_loop` still logged `retention purge queued for N companies` from the returned id list. A company's retention policy was therefore enforced only by a hand-queued job or the privacy purge endpoint. No test or gate covered the producer. **Fixed on `feat/v6` as a standalone bug fix:** the call now awaits, and `EnqueueDueRetentionTests` in `tests/test_worker.py` proves an opted-in company is enqueued with the right payload and a zero-day policy queues nothing. This is a defect repair, not a V6-20 start — the queue contract, retry policy and D9 are untouched.
2. **No delivery guarantee exists at the queue level.** Every type relies on its own record or its loop's next tick. `ingest` is the only type with an explicit stale claim (6 h) and startup recovery; `digest`, `topic_clusters` and `insights` use 30 min / `DIGEST_CHECK_SECONDS` claim windows; `retention` and `sitemap_scan` have no claim row at all.
3. **Duplicate external sends are possible for `digest`.** `sent_at` is stamped only after every recipient has been attempted, so a crash between "mail server accepted" and that commit re-sends the period. A partial send (`sent > 0`) stamps the period and never retries the failed recipients.
4. **Duplicate provider spend is possible for `topic_clusters` and `insights`** after a crash: their claims prevent concurrent runs, not a second run after the stale window.
5. **A `sitemap_scan` crash can leave knowledge stale until the refresh schedule**, because the page diff commits before the ingest is enqueued and a repeat scan sees no change to act on. A crash that lands after `claim_ingest` committed but before the enqueue is the milder case: the website row is stranded in `processing`, so `recover_stuck_ingests` re-enqueues it at the 6 h window.
6. **A deterministic failure repeats every interval** for `digest`, `topic_clusters` and `insights`, because their loops re-queue on a timer with no attempt counter. Nothing bounds the number of repeats; only the claim windows bound concurrency.
7. Everything above is observed on the current code; none of it is a behaviour change, a policy choice or a D9 decision.
8. **The scheduler loops held no reference to their own tasks — found and fixed.** `worker()` started its seven loops with bare `asyncio.create_task(...)` calls and kept none of the tasks; the event loop stores tasks weakly, so a loop that is still running can in principle be garbage-collected and its timer then stops silently. `start_background_loops()` now starts every loop through `_keep_task`, which holds it in the module-level `_background_tasks` set and releases it through a done-callback. The same loops start under the same conditions, so no job, queue or claim semantics changed. **Fixed on `feat/v6` (`ab7cb8a`)**; `BackgroundLoopRetentionTests` in `tests/test_worker.py` pins the reference set, the release on completion and the no-duplicate rule. The collection itself is not reproducible on CPython 3.13 — the loop's timer handle keeps a strong reference — so what is tested is the bookkeeping, not a collected task.
9. **A fire-and-forget email could fail silently, and the coroutine could be abandoned — found and fixed.** `send_email` schedules `send_email_async` when a loop is running and no caller holds the result, so an SMTP failure surfaced only as asyncio's garbage-collection warning; `_log_failed_send` now retrieves that exception and logs it without the recipient. The coroutine is also built before `loop.create_task`, so a loop that refuses the task (typically during shutdown) raised into the caller and left the coroutine un-awaited: the scheduling step is now guarded the way `integrations.emit_event` guards its own, closing the coroutine and logging the loss instead of raising. **Fixed on `feat/v6` (`ab7cb8a`, `88860c6`)**; `BackgroundSendLoggingTests` and `UnschedulableSendTests` in `tests/test_mail.py` cover the logged failure, the quiet success and the refused schedule. The SMTP failure is mocked and no shutdown-time `RuntimeError` was reproduced — only injected — so the loss is recorded, never retried.

## What this does not decide

- Whether the guarantee should be at-least-once, at-most-once or job-specific (D9).
- Whether to add acknowledgement/visibility-timeout, a reliable Redis processing list, or a database outbox.
- Retry limits, backoff, dead-letter ownership and the replay procedure.
- Any further code change: finding 1's missing `await` was repaired as a standalone bug fix (it restored the behaviour the loop already claimed), and nothing else recorded here is a change, a policy choice or a D9 decision.

The first three questions above are D9's, and the brief that records their options is `docs/preflight-v6.md` → `Appendix — D9 decision brief`: §1a carries the consequences of an acknowledgement list and of a durable job record for each of the six job types, and §6 the evidence matrix that would close V6-20 and gate V6-2G box 1. D9 is still **UNAPPROVED**, so this document still decides none of them.

## Scope V6-20 can settle before D9

D9 chooses *where* the delivery guarantee lives. Three things were true whichever option it picks and could therefore be built without pre-empting it: an in-flight job was not recorded anywhere, a failure left nothing but a log line, and there was no place the chosen mechanism could later be dropped in. This section records the gap inventory per type, the three gaps no delivery mechanism closes, and the seam that was **implemented on 2026-11-26** on that reasoning.

### What the matrix leaves open, per type

The matrix above states each type's recovery path. This is the part of each path that is **delivery**, not handler semantics — the message is in the worker's memory from `BRPOP` (`worker.py:268`) and a crash, a deploy or a handler exception removes it with nothing left to replay from.

| Job type | Delivery gap left open | Why its own claim does not close it | Closed by a queue-level delivery record? |
|---|---|---|---|
| **`ingest`** | A crash between the pop and `handle_ingest`'s first commit loses the job; the row stays `processing` until `STUCK_INGEST_AFTER` (6 h) and `recover_stuck_ingests` re-queues it. | The claim is taken by the **producers** (`worker.py:946`), never consulted by the handler, so it records "a crawl is due", not "this delivery is being attempted". | The lost message, yes — a retry inside the retry window instead of 6 h. It does **not** make the redelivery safe; that is the handler's missing claim check, which D9 has to classify. |
| **`digest`** | A lost message waits for the next `digest_hour` (up to 24 h). A crash between the mail server accepting and `sent_at` committing (`services/digest.py:491`) leaves an unsent claim that `claim_period` takes over once it is older than `DIGEST_CHECK_SECONDS` (1 h), so the period is sent again at the next send hour; a partial send (`sent > 0`) stamps the period and never retries the failed recipients. | `digest_log` records the **period**, not the delivery, and `sent_at` is written after the external side effect. | The lost message, yes. The duplicate and the partial send, **no** — see *Three gaps that are not delivery problems*. |

Across the six, at this snapshot: **0 of 6** types have a delivery record, **2 of 6** (`retention`, `sitemap_scan`) have no claim of any kind, **6 of 6** have no attempt counter, and a failed job is visible only as a `worker.job.failed` line plus the `ops:worker:job_failures` counter (findings 2, 6 and 7).

### Three gaps that are not delivery problems

These are handler and side-effect windows. No acknowledgement mechanism closes them, and building one here would not change them:

1. **`digest` duplicate and partial send.** The duplicate comes from `sent_at` being stamped after the mail server accepted, and the missing recipient retry from `sent == 0` being the only path that releases the claim. Closing them needs a pre-send stamp or a provider idempotency key and a per-recipient record — a side effect, not a delivery. Whether a repeat is acceptable for a digest at all is D9 §2's per-type classification.
2. **`sitemap_scan` diff-then-enqueue.** The page diff commits, then the ingest is claimed and enqueued as separate steps. Closing it means recording the intended ingest in the same commit as the diff (or holding the sitemap job until the ingest is enqueued), which is what the durable-record option makes possible and the acknowledgement list only makes retryable.
3. **`ingest` redelivery.** `handle_ingest` sets `processing` itself instead of consulting `claim_ingest`, so a redelivered job re-crawls and re-embeds while another worker's crawl of the same site may be running. Adding the check changes the type from at-least-twice to at-most-once while the row says `processing`, which is the choice D9 §2 has to name — so it waits.

### The mechanism-neutral seam

Both D9 candidates need the same four things — a stable job identity, an in-flight state, a completion/failure transition carrying an attempt count, and one place that runs them — and differ only in where that state lives and how the next job is fetched. The shared part is what was built: three additive pieces, no migration, no new dependency, no new flag and no behaviour change. The differing part is deliberately not written.

1. **A job envelope**, minted in `services/redis.py::enqueue_job` — the single place every producer already goes through — and normalised at pop time in `worker.worker()`: `{"type": …, "job_id": "<uuid4>", "attempt": 0, …}`. `type` stays at the top level, so existing readers, the test suite and the gate's `redis-cli LPUSH` recipes keep working; a legacy payload with no `job_id` is accepted and given one when it is popped, with `attempt: 0`, while an envelope that is already there is preserved verbatim.
2. **One seam**, `services/delivery.py`, with the smallest interface both candidates implement unchanged:
   ```python
   claim(job)       -> Claim | None   # record the attempt; None = already done / parked
   complete(claim)  -> None            # the handler returned
   fail(claim, exc) -> Outcome         # attempt += 1; retry or park (the limit is D9 §3)
   ```
   and exactly one call site: the `try`/`except` around `await handler(data)` in `worker.worker()`.
3. **One implementation, `NullDelivery`**, whose `claim` costs nothing, whose `complete` is a no-op and whose `fail` does what the loop did before the seam — the structured `worker.job.failed` event (now carrying `job_id` and `attempt`) and the `ops:worker:job_failures` increment — and nothing else. The consumer and every handler kept their signatures and semantics, and D9 drops in the second implementation without touching either: the acknowledgement list becomes `LMOVE queue:jobs -> queue:processing:<worker>`, `LREM` on complete, re-push with `attempt + 1` or a dead list on failure, plus a reaper; the durable record becomes an insert/`FOR UPDATE SKIP LOCKED` claim, terminal and `not_before` updates, its M13 migration and a settle rule.

**What changed today: nothing observable.** `NullDelivery` records no attempt, retries nothing and parks nothing, which is exactly the old loop's behaviour; a hand-pushed payload still runs, an unknown type is still skipped without a claim, and one failure is still one event and one counter increment. **What it makes possible:** every job now has an id and an attempt number, an in-flight job has a place to be recorded, and a failure carries the identity an operator or a replay procedure needs — the four things both D9 candidates were going to need anyway. A lost message still waits for the next tick, hour or day until a mechanism is chosen.

**Not built, on purpose:** the visibility layer an earlier version of this plan listed — an `ops:worker:inflight` gauge and `worker.job.claimed`/`completed`/`retried`/`parked` events — because where a failed job is surfaced is D9 §4, and a gauge over a count nothing durably queries would suggest a guarantee this implementation does not provide. The only new telemetry is the two additive fields on the existing failure event.

**What it leaves open — D9's four questions, unchanged:** at-least-once vs at-most-once vs per type (§2), acknowledgement list vs durable record (§1), retry limit, backoff, dead-letter ownership and replay procedure (§3), and where a failed job is surfaced (§4). It also leaves the three handler windows above exactly as they are.

**Tests and the re-run.** `tests/test_worker_delivery.py` is new (13 cases): the envelope's additive contract through `enqueue_job` (field for field, plus distinct ids), a legacy payload normalised at pop time, an existing envelope preserved, a malformed id or attempt replaced rather than trusted, `next_attempt` counting up without moving the id; one claim per job, with `complete` on return, `fail` on a raise, two claims for two jobs and an unknown type never claimed; and the unchanged failure count — one event, one `note_failure` call with the worker's own client, `retry=False`, and the loop counting through the hook it always used. `tests/test_redis_helpers.py`'s old exact-payload pin was replaced by an additive-contract pin (`test_enqueue_payload_is_additive`), which still asserts every producer field by name. Recorded 2026-11-26: full suite **79 modules / 1340 Python tests OK**, `node --test tests/*.mjs` **46/46**, Alembic head unchanged at `0b22b30bf930`; gate V6-2G re-run through `scripts/gate_v6_2g/run_disposable_redis.sh` — **11 passed, 3 blocked (items 6, 8, 12), 0 failed**, exit 0, identical to the run recorded above, with item 5 `Repeated job failure` passing at `ops:worker:job_failures -> 3` and item 13 `Graceful shutdown` passing on a hand-pushed payload that carries no envelope, which exercises the pop-time normalisation path for real.

**Sequence:** this was the first V6-20 commit — a refactor plus two additive log fields, with no policy in it. The replay/dead-letter procedure can be written in the same mechanism-neutral form (job id, outcome, who may re-push), but its pass conditions in the D9 brief's §6 stay unmet until the second implementation exists.
