## Findings that belong to V6-20

1. **The retention scheduler enqueued nothing — found and fixed.** `worker.enqueue_due_retention` (`worker.py:506`) called `enqueue_job({...})` without `await`, and `enqueue_job` is a coroutine (`services/redis.py:152`): the call produced a never-awaited coroutine, pushed nothing, and `retention_loop` still logged `retention purge queued for N companies` from the returned id list. A company's retention policy was therefore enforced only by a hand-queued job or the privacy purge endpoint. No test or gate covered the producer. **Fixed on `feat/v6` as a standalone bug fix:** the call now awaits, and `EnqueueDueRetentionTests` in `tests/test_worker.py` proves an opted-in company is enqueued with the right payload and a zero-day policy queues nothing. This is a defect repair, not a V6-20 start — the queue contract, retry policy and D9 are untouched.
2. **No delivery guarantee exists at the queue level.** Every type relies on its own record or its loop's next tick. `ingest` is the only type with an explicit stale claim (6 h) and startup recovery; `digest`, `topic_clusters` and `insights` use 30 min / `DIGEST_CHECK_SECONDS` claim windows; `retention` and `sitemap_scan` have no claim row at all.
3. **Duplicate external sends are possible for `digest`.** `sent_at` is stamped only after every recipient has been attempted, so a crash between "mail server accepted" and that commit re-sends the period. A partial send (`sent > 0`) stamps the period and never retries the failed recipients.
4. **Duplicate provider spend is possible for `topic_clusters` and `insights`** after a crash: their claims prevent concurrent runs, not a second run after the stale window.
5. **A `sitemap_scan` crash can leave knowledge stale until the refresh schedule**, because the page diff commits before the ingest is enqueued and a repeat scan sees no change to act on. A crash that lands after `claim_ingest` committed but before the enqueue is the milder case: the website row is stranded in `processing`, so `recover_stuck_ingests` re-enqueues it at the 6 h window.
6. **A deterministic failure repeats every interval** for `digest`, `topic_clusters` and `insights`, because their loops re-queue on a timer with no attempt counter. Nothing bounds the number of repeats; only the claim windows bound concurrency.
7. Everything above is observed on the current code; none of it is a behaviour change, a policy choice or a D9 decision.
8. **The scheduler loops held no reference to their own tasks — found and fixed.** `worker()` started its seven loops with bare `asyncio.create_task(...)` calls and kept none of the tasks; the event loop stores tasks weakly, so a loop that is still running can in principle be garbage-collected and its timer then stops silently. `start_background_loops()` now starts every loop through `_keep_task`, which holds it in the module-level `_background_tasks` set and releases it through a done-callback. The same loops start under the same conditions, so no job, queue or claim semantics changed. **Fixed on `feat/v6` (`ab7cb8a`)**; `BackgroundLoopRetentionTests` in `tests/test_worker.py` pins the reference set, the release on completion and the no-duplicate rule. The collection itself is not reproducible on CPython 3.13 — the loop's timer handle keeps a strong reference — so what is tested is the bookkeeping, not a collected task.
9. **A fire-and-forget email could fail silently, and the coroutine could be abandoned — found and fixed.** `send_email` schedules `send_email_async` when a loop is running and no caller holds the result, so an SMTP failure surfaced only as asyncio's garbage-collection warning; `_log_failed_send` now retrieves that exception and logs it without the recipient. The coroutine is also built before `loop.create_task`, so a loop that refuses the task (typically during shutdown) raised into the caller and left the coroutine un-awaited: the scheduling step is now guarded the way `integrations.emit_event` guards its own, closing the coroutine and logging the loss instead of raising. **Fixed on `feat/v6` (`ab7cb8a`, `88860c6`)**; `BackgroundSendLoggingTests` and `UnschedulableSendTests` in `tests/test_mail.py` cover the logged failure, the quiet success and the refused schedule. The SMTP failure is mocked and no shutdown-time `RuntimeError` was reproduced — only injected — so the loss is recorded, never retried.

- Whether to add acknowledgement/visibility-timeout, a reliable Redis processing list, or a database outbox.
- Retry limits, backoff, dead-letter ownership and the replay procedure.
- Any further code change: finding 1's missing `await` was repaired as a standalone bug fix (it restored the behaviour the loop already claimed), and nothing else recorded here is a change, a policy choice or a D9 decision.

## Scope V6-20 can settle before D9

D9 chooses *where* the delivery guarantee lives. Three things were true whichever option it picks and could therefore be built without pre-empting it: an in-flight job was not recorded anywhere, a failure left nothing but a log line, and there was no place the chosen mechanism could later be dropped in. This section records the gap inventory per type, the three gaps no delivery mechanism closes, and the seam that was **implemented on 2026-11-26** on that reasoning.

### What the matrix leaves open, per type

The matrix above states each type's recovery path. This is the part of each path that is **delivery**, not handler semantics — the message is in the worker's memory from `BRPOP` (`worker.py:268`) and a crash, a deploy or a handler exception removes it with nothing left to replay from.

Across the six, at this snapshot: **0 of 6** types have a delivery record, **2 of 6** (`retention`, `sitemap_scan`) have no claim of any kind, **6 of 6** have no attempt counter, and a failed job is visible only as a `worker.job.failed` line plus the `ops:worker:job_failures` counter (findings 2, 6 and 7).

### Three gaps that are not delivery problems

These are handler and side-effect windows. No acknowledgement mechanism closes them, and building one here would not change them:

1. **`digest` duplicate and partial send.** The duplicate comes from `sent_at` being stamped after the mail server accepted, and the missing recipient retry from `sent == 0` being the only path that releases the claim. Closing them needs a pre-send stamp or a provider idempotency key and a per-recipient record — a side effect, not a delivery. Whether a repeat is acceptable for a digest at all is D9 §2's per-type classification.
2. **`sitemap_scan` diff-then-enqueue.** The page diff commits, then the ingest is claimed and enqueued as separate steps. Closing it means recording the intended ingest in the same commit as the diff (or holding the sitemap job until the ingest is enqueued), which is what the durable-record option makes possible and the acknowledgement list only makes retryable.
3. **`ingest` redelivery.** `handle_ingest` sets `processing` itself instead of consulting `claim_ingest`, so a redelivered job re-crawls and re-embeds while another worker's crawl of the same site may be running. Adding the check changes the type from at-least-twice to at-most-once while the row says `processing`, which is the choice D9 §2 has to name — so it waits.

### The mechanism-neutral seam

Both D9 candidates need the same four things — a stable job identity, an in-flight state, a completion/failure transition carrying an attempt count, and one place that runs them — and differ only in where that state lives and how the next job is fetched. The shared part is what was built: three additive pieces, no migration, no new dependency, no new flag and no behaviour change. The differing part is deliberately not written.

1. **A job envelope**, minted in `services/redis.py::enqueue_job` — the single place every producer already goes through — and normalised at pop time in `worker.worker()`: `{"type": …, "job_id": "<uuid4>", "attempt": 0, …}`. `type` stays at the top level, so existing readers, the test suite and the gate's `redis-cli LPUSH` recipes keep working; a legacy payload with no `job_id` is accepted and given one when it is popped, with `attempt: 0`, while an envelope that is already there is preserved verbatim.
2. **One seam**, `services/delivery.py`, with the smallest interface both candidates implement unchanged:
   ```python
   claim(job)       -> Claim | None   # record the attempt; None = already done / parked
   complete(claim)  -> None            # the handler returned
   fail(claim, exc) -> Outcome         # attempt += 1; retry or park (the limit is D9 §3)
   ```
   and exactly one call site: the `try`/`except` around `await handler(data)` in `worker.worker()`.
3. **One implementation, `NullDelivery`**, whose `claim` costs nothing, whose `complete` is a no-op and whose `fail` does what the loop did before the seam — the structured `worker.job.failed` event (now carrying `job_id` and `attempt`) and the `ops:worker:job_failures` increment — and nothing else. The consumer and every handler kept their signatures and semantics, and D9 drops in the second implementation without touching either: the acknowledgement list becomes `LMOVE queue:jobs -> queue:processing:<worker>`, `LREM` on complete, re-push with `attempt + 1` or a dead list on failure, plus a reaper; the durable record becomes an insert/`FOR UPDATE SKIP LOCKED` claim, terminal and `not_before` updates, its M13 migration and a settle rule.

**What changed today: nothing observable.** `NullDelivery` records no attempt, retries nothing and parks nothing, which is exactly the old loop's behaviour; a hand-pushed payload still runs, an unknown type is still skipped without a claim, and one failure is still one event and one counter increment. **What it makes possible:** every job now has an id and an attempt number, an in-flight job has a place to be recorded, and a failure carries the identity an operator or a replay procedure needs — the four things both D9 candidates were going to need anyway. A lost message still waits for the next tick, hour or day until a mechanism is chosen.

**Not built, on purpose:** the visibility layer an earlier version of this plan listed — an `ops:worker:inflight` gauge and `worker.job.claimed`/`completed`/`retried`/`parked` events — because where a failed job is surfaced is D9 §4, and a gauge over a count nothing durably queries would suggest a guarantee this implementation does not provide. What the seam does add is a label, not a new signal: `job_id` and `attempt` on the three events about a job that already existed — `worker.job.received`, `worker.job.unknown` and `worker.job.failed` — so one job can be followed from the pop to its failure (and a hand-pushed job, whose id is minted at pop time) without a new event, a new counter, or any state a mechanism would own.

**What it leaves open — D9's four questions, unchanged:** at-least-once vs at-most-once vs per type (§2), acknowledgement list vs durable record (§1), retry limit, backoff, dead-letter ownership and replay procedure (§3), and where a failed job is surfaced (§4). It also leaves the three handler windows above exactly as they are.

**Tests and the re-run.** `tests/test_worker_delivery.py` is new (24 cases): the envelope's additive contract through `enqueue_job` (field for field, plus distinct ids), a legacy payload normalised at pop time, an existing envelope preserved, a malformed id or attempt replaced rather than trusted, `next_attempt` counting up without moving the id; one claim per job, with `complete` on return, `fail` on a raise, two claims for two jobs and an unknown type never claimed; and the unchanged failure count — one event, one `note_failure` call with the worker's own client, `retry=False`, the loop counting through the hook it always used; and that the `job_id`/`attempt` on `worker.job.received`, `worker.job.unknown` and `worker.job.failed` are the same for one job, including for a payload that carried no envelope. `tests/test_redis_helpers.py`'s old exact-payload pin was replaced by an additive-contract pin (`test_enqueue_payload_is_additive`), which still asserts every producer field by name.

**The second implementation, in tests only.** `tests/test_worker_delivery.py::AckListDelivery` is an acknowledgement list written against nothing but the same three calls — `claim` marks an id in flight (and answers `None` for one already claimed), `complete` drops it, `fail` drops it and increments the attempt — and the consumer scenarios above run through it by replacing `worker.NullDelivery`, the one name the loop already reads. The handled-job, raising-handler, unknown-type and redelivery cases pass with it, a redelivery of the same `job_id` is claimed at `attempt 1` after a failure, and two copies of a payload with no id each get their own id and both run. So the three calls are enough for a mechanism that keeps state, and the duplicate rule stays D9 §2's: no line of `worker.worker()`, no handler and no `src/` module knows the class exists. Recorded 2026-11-26: full suite **79 modules / 1351 Python tests OK**, `node --test tests/*.mjs` **46/46**, Alembic head unchanged at `0b22b30bf930`; gate V6-2G re-run through `scripts/gate_v6_2g/run_disposable_redis.sh` — **11 passed, 3 blocked (items 6, 8, 12), 0 failed**, exit 0, with the gate now asserting this seam's evidence rather than just the counts: item 5 `Repeated job failure` pairs three `worker.job.received` lines with three `worker.job.failed` lines by `job_id` and requires `attempt` and `job_type` to match on each, and item 13 `Graceful shutdown` sends `kill -TERM` into two job types, a `digest` build and then a `retention` purge, each held on a table lock — both finish (11.0 s, 10.9 s) before `worker.stopped {"graceful":true}` with no `worker.job.failed`, and the hand-pushed payloads carry no envelope, which exercises the pop-time normalisation path for real.

**Sequence:** this was the first V6-20 commit — a refactor plus two additive log fields, with no policy in it. The replay/dead-letter procedure can be written in the same mechanism-neutral form (job id, outcome, who may re-push), but its pass conditions in the D9 brief's §6 stay unmet until the second implementation exists.

## What a crash, a duplicate and an unknown actually do (rehearsal)

Everything above is read from the code. This section is the same six types **run**, with the worker killed, a payload delivered twice and a payload nothing handles, so the recovery column stops being an inference. Recorded 2026-11-26 on commit `ff17bc1`, Alembic head `0b22b30bf930`:

```
bash scripts/v6_20_rehearsal/run.sh
```

That wrapper starts its own `redis:6.2` container on a random loopback port, runs the rehearsal against a throwaway database `v6_gate_2g_rehearsal` (created and dropped by the run), and removes the container afterwards. The shared PostgreSQL server is never stopped and the shared Redis is never contacted. Every observation is the worker's own JSON log plus the rows the rehearsal reads back; no handler is patched and no fault is simulated inside the code. The full row output was rows.md in the run's log directory.

### A crash mid-job

`kill -9` was sent 0.5 s after `worker.job.received` appeared for the pushed `job_id`, with a table the handler must read held by an `ACCESS EXCLUSIVE` lock, so the job is provably inside its handler when the process dies. A second, fresh worker then ran for 8 s with no help, and only after that was the type's own scheduler function called.

| Type | What the kill left behind | A fresh worker, 8 s, unhelped | The recovery path that actually ran | How long it waits in production |
|---|---|---|---|---|
| **`ingest`** | `websites.ingest_status=processing` | nothing: the killed `job_id` never reappears, no new `ingest` job | `requeue_stuck_ingests` re-queued it after the row was backdated -7 h; the fresh worker consumed it and the ingest completed | up to `STUCK_INGEST_AFTER` — 6 h |
| **`digest`** | a `digest_log` claim row with `sent_at` NULL | nothing | `enqueue_due_digests` re-queued it after the claim was backdated -2 h; the fresh worker consumed it | up to `DIGEST_CHECK_SECONDS` (1 h) before the claim is retakeable, then the next send hour |
| **`retention`** | nothing durable (the duplicate run below had already purged the rows, so the killed purge had nothing left to lose) | nothing | `enqueue_due_retention` re-queued it on the next tick | up to `RETENTION_CHECK_SECONDS` — 24 h |
| **`topic_clusters`** | the `topic_cluster_runs` row left `running` | nothing | `enqueue_due_topics` re-queued it after the run row was backdated -31 min; a second run completed while the killed row stayed `running` | up to `STALE_RUN_AFTER` — 30 min |
| **`sitemap_scan`** | nothing durable; the `sitemap:scan:<website_id>` key absent | nothing | `enqueue_due_sitemap_scans` re-queued it, and the scan set the key | up to `SITEMAP_SCAN_INTERVAL_SECONDS` — 24 h |
| **`insights`** | nothing durable | nothing | `enqueue_due_insights` re-queued it | up to `INSIGHT_INTERVAL_SECONDS` — 24 h |

Two things in that table are the point of the rehearsal. **A crash is invisible to the process.** In all six cases, a replacement worker started and did nothing about the job that had just died — no redelivery, no compensation, not even a `worker.job.failed` line, because the process that would have written one is gone. The only thing that ever recovered the work was the type's own stale-row rule or its loop tick, and for four of the six types that rule does not exist, so the wait is a full day. And **the left-behind state is a claim, not a delivery record**: `ingest` leaves `processing`, `digest` leaves an unsent period, `topic_clusters` leaves `running`, and the other three leave nothing at all. That is exactly the gap D9 §1 has to close, now measured rather than argued.

### The same payload delivered twice

One worker, the byte-identical payload pushed twice (same `job_id`, `attempt: 0`, so this is a producer replay, not a retry):

| Type | Runs observed | What the second one did |
|---|---|---|
| **`ingest`** | 2 × `worker.job.received`, 2 × `ingest.completed` | crawled and re-embedded the whole site again; the handler never consults `claim_ingest`, so nothing suppressed it |
| **`digest`** | 2 × `digest.period_completed`, both `reason: no recipients configured` | claimed, built, found no recipients and released the claim — so with recipients configured the second run would build again; nothing carried over from the first |
| **`retention`** | 2 × `retention.purged` | first deleted 203 `chat_messages` and 2 `conversations`; second deleted 0. Idempotent through the age cutoff, not through a record |
| **`topic_clusters`** | `topics.window_built` `completed`, then `skipped` | the unique run row suppressed the repeat — the one type whose own claim rejects a duplicate outright |
| **`sitemap_scan`** | 2 × `sitemap.nothing_changed` | fetched and diffed again (the rehearsal has no network, so the fetch failed and the handler returned before touching a row) |
| **`insights`** | 2 × `insights.run_completed`, both `status: skipped, eligible: 0` | the per-conversation claim had nothing to claim in this fixture; with eligible conversations the second batch would re-run whatever the first left `failed` |

This is D9 §2's input, not its answer: today a duplicate is harmless for `retention` and `topic_clusters`, repeats real work for `ingest` and `sitemap_scan`, and would repeat a send for `digest` once recipients exist. Which of those is acceptable per type is the question D9 has to name.

### A payload nothing handles

`LPUSH queue:jobs '{"type":"rehearsal.unhandled"}'` was consumed (queue depth back to 0) with one `worker.job.received` and one `worker.job.unknown` sharing the same `job_id`, **no** `worker.job.failed`, and `ops:worker:job_failures` unchanged at 0. So an unknown type is dropped silently by the counter the V6-21 alert reads — it is a log line and nothing else. That is also why the identity work matters: without `job_id` on both lines, the pop and the skip could only be matched by timestamp.

### The shortcuts, stated

* **Mid-job is a held table lock**, the trick gate item 13 already uses: `embeddings` for `ingest` (after the row is `processing`), `chat_messages` for `digest` and `retention`, `topic_clusters` for `topic_clusters`, `websites` for `sitemap_scan`, `conversation_insights` for `insights`. The handler is blocked inside the job, which is what "mid-job" means when there is no network to slow a crawl down.
* **The waits were not sat through.** Where the recovery is time-gated, the rehearsal backdated the one column that gates it (`websites.updated_at` -7 h, `digest_log.created_at` -2 h, `topic_cluster_runs.updated_at` -31 min) and then called the real scheduler function in a child process with the application environment. The observation is what the next tick would do; the row and column are printed beside it, so the shortcut is visible in the output, not just here.
* **No network, no SMTP, no model provider.** So `sitemap_scan` sees an empty fetch, `digest` finds no recipients, `insights` finds nothing eligible, and `ingest` crawls nothing — the embed of one seeded extra document is the work that makes its crash window reachable. Every one of those is reported in the row as the reason the handler finished the way it did.

**What this does not do.** It ticks no box in `plans/PLAN_V6.md`: V6-20 stays unticked, gate V6-2G box 1 stays unsignable, and the D9 brief's §6 pass conditions are unchanged. It decides none of D9's four questions — it does not say whether a lost job is acceptable, whether a duplicate is, what the retry limit should be, or where a failure should be surfaced. It measures the behaviour those questions are about, on the day of the run, so the answer can be chosen against numbers instead of a reading of the code.
