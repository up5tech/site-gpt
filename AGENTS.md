# AGENTS.md

Instructions for AI coding agents working in this repo. Backend = FastAPI (Python 3.13, `src/site_gpt/`), frontend = React+Vite+TS (`frontend/`).

## Run / verify

```bash
source .venv/bin/activate
uv run uvicorn site_gpt.app.main:app --reload   # API :8000
uv run python -m site_gpt.app.worker            # ingest worker, separate terminal
uv run alembic upgrade head                     # apply migrations
cd frontend && npm run dev                      # UI :5173 (VITE_BACKEND_URL=http://localhost:8000)
```

Unit tests use plain `unittest` (no extra deps): `uv run python -m unittest discover -s tests -v` — covers `split_text`, `extract_text_from_file`, `collect_sources`, `format_history`, `_client_ip`, the settings registry/allowlist, and the V2 services (`build_digest`, `render_digest_html`, `normalize_period`, `claim_period`, `rebuild_qa_document`, `emit_event_async`, API-key hashing/lookup). The widget's browser helpers are tested separately with node's built-in runner: `node --test tests/*.mjs` — `widget_bootstrap.test.mjs` pins the bootstrap's shape, while `widget_session_token.test.mjs` evaluates the real `ensureSessionToken` with stubs (fake `fetch` statuses, storage, `newSession`) so the 403 reset-and-mint-once behaviour is executed, not pattern-matched (there is deliberately no npm `test` script; `tests/test_widget_markdown.py` also shells out to node so `unittest discover` fails if it is missing and the tests regress). Also verify by import/compile: `uv run python -c "import site_gpt.app.main"` and `cd frontend && npm run build`.

Run the suite (or a single file: `uv run python -m unittest tests.test_settings -v`) after changing services under `src/site_gpt/app/services/` or the settings keys.

## Layout & ownership

- `src/site_gpt/app/main.py` — app + CORS (open, dev only) + router wiring. Add new routers here with `/api/...` prefix.
- `src/site_gpt/app/api/` — one module per resource; `routes.py` holds auth/chat/ingest/widget endpoints. Routers define full paths internally or rely on prefix in `main.py` — check before adding routes. `api/v1.py` (`/api/v1`, `X-API-Key` via `core/auth.get_api_key` + `require_scope`) reuses `claim_ingest` / `ensure_website_active` / `ensure_embed_allowed`; `api/api_key.py` (`/api/api-keys`, admin) mints and revokes keys through `services/api_keys.py` (SHA-256 + `API_KEY_PEPPER`, raw key returned once, never stored). `api/privacy.py` (`/api/privacy`, admin) owns the export and the two erasure endpoints — the conversation erasure goes through `services.conversations.erase_session` (messages, inbox row, feedback, handoffs and that session's `session_tokens` in one transaction; the export lists the inbox state too) rather than deleting rows by hand, and both routes stay company-scoped (a foreign `website_id` is a 404, not a 403). `api/inbox.py` (`/api/inbox`, V3-41) is the agent console: manager+ **and** the company's `live_inbox_enabled` flag via the `live_inbox_user` dependency (a 404 for the whole surface when it is off, while the public handoff keeps working), six routes — paginated queue list, detail with transcript/contact, and claim/assign/release/close — each answering 404 for a foreign conversation and 409 for a refusal, and none of them writing a row itself. V3-42 adds `GET /api/inbox/events` (SSE meant for `fetch()` streaming, because `EventSource` cannot carry the `Authorization` header: the flag and a `redis.ping()` are checked **before** the `StreamingResponse`, so off is a 404 and Redis down is a 503 rather than a stream that never delivers) and `GET /api/inbox/presence` (per-agent connection counts from Redis leases, an empty list when Redis is unreachable); the four action routes stay plain `def` (a claim's `FOR UPDATE` transaction must not run on the event loop and stall every open stream) and hand their notification to `inbox.publish_after_commit` — a queue put, drained by one daemon thread with its own loop and client — **after** the service committed. V3-43 adds `POST /conversations/{id}/messages` (an agent reply, stored `role='agent'` with its author, holder-only and only while `human`, published after the commit on both the inbox channel and the visitor's own stream) and, in `routes.py`, the public `GET /api/chat/messages` (keyset cursor) and `GET /api/chat/messages/stream` (SSE) that carry it to the widget; both are K4-authorized and answer 503 before streaming when Redis is down, so the widget polls instead. The admin transcript types (`types/api.ts`, `ChatContext`) accept `agent` too, so a human-answered session does not read as if the bot wrote it. V3-44 adds `GET /api/inbox/status` (manager+, `InboxStatus`) which answers `{enabled}` instead of the surface's 404 so the console navigation can gate on the flag — `frontend/src/pages/Inbox.tsx` renders the queue, transcript, composer, Claim/Release/Close and presence, re-reads the queue/detail/presence on every event frame and reconnects with backoff, and `Layout.tsx` only links `/inbox` when the status says enabled, and an admin switches the flag on in Settings → Appearance → Live-agent inbox, which writes it through the existing admin-only `PUT /api/settings` and fires `INBOX_STATUS_CHANGED` so the navigation re-reads the status without a reload. V3-45 makes `POST /api/handoff` a queue entry only for a company with the inbox on: it asks `inbox_service.enabled` and, when true, calls `conversations.mark_waiting` in the same transaction as the handoff row (create or reuse, idempotent), while with the flag off the V2.1 path is unchanged and no `conversations` row appears; the `handoff.requested` payload gains `conversation_id`/`conversation_state` additively, and `services/inbox.py::_sync_handoff` moves the session's handoff row to `accepted` (claim/assign), `pending` (release) or `closed` (close) inside each transition. The widget's live path is gated the same way: `widget.js` streams/polls only while the session is `waiting` or `human` (started by a queued reply or a handoff, and by a restored history whose `state` is engaged), the read endpoints return `state`, the console's claim/release/close publish a `state` frame on the session channel, and a closed session (or a `409` from the stream route) stops the timer and aborts the socket. `api/integration.py`, `api/digest.py`, `api/analytics.py`, `api/feedback.py` and `api/handoff.py` are the other V2 routers. `api/analytics.py` is the manager+ analytics surface: `GET /api/analytics/summary` (the digest's V3 counts plus V4's additive `trend`/`funnel`/`top_questions`, `days` clamped `1..90`, and V4-43's `outcomes` breakdown **only** for a company with `conversation_insights_enabled` on — the key is absent, not null, otherwise, so a V3 client reads the V4-1G payload byte for byte) and `GET /api/analytics/export.csv` (a `Response`, `text/csv` with a `Content-Disposition` filename — company-derived like the summary and deliberately **not** mirrored under `/api/v1`, where `analytics/summary` is the only keyed analytics route).

## Conventions

- Python: SQLAlchemy 2.0 `Mapped/mapped_column` style, `Session = Depends(get_db)`, JWT via `core/auth.py` (`hash_password`/`verify_password`/`create_access_token`). Don't introduce new auth libs.
- Embeddings are `Vector(EMBEDDING_DIMENSIONS)` (default 1536) — the embedding model's output dimension must match `EMBEDDING_DIMENSIONS`; changing it requires an Alembic migration + re-ingest. `EMBEDDING_AI` selects the embedding provider independently of the chat provider `LLM_AI`.
- Chunking: `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)` — keep consistent between `ingest.py` and new code.
- RAG search SQL lives in `rag.py::search` (single query over `embeddings` joined to `documents` **and** `extra_documents`, top 5, website-scoped with company-wide extra documents). Extend there, don't duplicate.
- Settings keys: appearance/widget keys go in `DEFAULT_SETTINGS`, server-side keys (models, emails, digest, quotas) in `INTERNAL_SETTINGS`; both seed registration and `POST /api/settings` through `ALL_SETTINGS`. `WIDGET_PUBLIC_KEYS` is an explicit literal tuple — a key is public only if you add it there deliberately, so never derive it from a registry dict.
- Mail is async: use `send_email_async(...)` (await it) in async code or worker jobs; `send_email(...)` is only a sync wrapper for sync endpoints and never blocks a running loop.
- Worker jobs are `{"type": "ingest", "website_id": ...}` on Redis list `queue:jobs` (types: `ingest`, `digest`, `retention`, `topic_clusters`, `sitemap_scan`, `insights` — V4 F4's scan carries `website_id`, is queued by `sitemap_loop` only for an opted-in company's `active` websites with a sitemap URL, tracks its last run in the best-effort Redis key `sitemap:scan:<website_id>`, and changes nothing unless a fully successful non-empty sitemap fetch came back — `handle_sitemap_scan` retires vanished pages and deletes every document row of the retired URL — not only the first, unlike `api/website.py`'s `/pages/{id}` delete, which still takes `.first()` — then queues one ingest through `claim_ingest` only if something changed); V4 F2's `insights` job carries `company_id` alone, is queued by `insight_loop` every `INSIGHT_INTERVAL_SECONDS` for a company with `conversation_insights_enabled`, and hands the work to `insights.run_for_company` — the loop decides only *whether* to queue, while the run owns the caps and the per-conversation claims; `handle_ingest` in `worker.py` sets `websites.ingest_status` (`none → processing → completed`), and `topic_loop` queues the last complete digest week for companies with `topic_clustering_enabled=true` once per `TOPIC_CLUSTER_INTERVAL_SECONDS`, leaving the claim, caps and completion to `topics.run_window`; one run costs exactly one `embed_texts` call over ≤ `TOPIC_CLUSTER_MAX_MESSAGES` (500) questions truncated to `MAX_QUESTION_CHARS` (1000) and at most one temperature-0 naming call over ≤ `MAX_CLUSTERS` (8) groups × `NAMING_SAMPLES` (5), which is the bounded provider cost `docs/security.md` §4 documents. `enqueue_due_digests` targets that same `digest.previous_period` and, for an opted-in company whose window is not settled, queues the `topic_clusters` job **before** the digest job — the queue is FIFO (`lpush` + `brpop`), so the digest reads a completed run instead of falling back to term counts.
- Frontend: axios through `utils/api.ts`, Ant Design for UI, `VITE_BACKEND_URL` for base URL. No new UI framework.
- Uploads go to `uploads/` with metadata in `attachments` table (`status='tmp'` default).

The author column is nullable and its FK is added `NOT VALID` then `VALIDATE CONSTRAINT`, so the busy `chat_messages` table takes no write-blocking lock; the new table's indexes are transactional, like M7/M8). Chain new migrations from the current head and keep a single linear head.
- **Indexes on busy tables are built `CONCURRENTLY`.** A plain `CREATE INDEX` takes a SHARE lock and blocks every write for the whole build, so new index migrations use `with op.get_context().autocommit_block(): op.create_index(..., postgresql_concurrently=True)` — see `d2f5a81c9b74` and `e7b3c94a1d52`. Caveats: `CONCURRENTLY` cannot run inside a transaction, so those migrations are **not atomic** (each index commits on its own and a later failure leaves the earlier ones in place); an interrupted build leaves an **invalid** index that the planner ignores but every write still maintains — drop it with `DROP INDEX CONCURRENTLY` and re-run the migration (it is not idempotent); `DROP INDEX CONCURRENTLY` needs the same autocommit block.
- Autogenerate always proposes drift: naive `DateTime()` ALTERs for the timestamptz columns (`api_keys.last_used_at`/`revoked_at`, `users.reset_token_expires_at`, `contacts.consent_at`) and a drop/create of `chat_feedback.website_id`'s FK. Remove those lines; keep only the real change.

## Do / don't

- DO reuse existing service helpers (`get_llm`, `get_embedding_model`, `embed_texts`, `enqueue_job`) instead of new clients.
- DO guard public endpoints with `services/embed_guard.ensure_embed_allowed`, check a website is servable with `services/website_state.ensure_website_active`, and claim ingests with `services/ingest_claim.claim_ingest` — never re-implement any of them in a route; a copy of the claim re-opens the double-crawl race. An embed-token refusal must never reset the visitor's session (the widget resets only for K4's `session_expired`), and `/api/v1` passes `require_embed_token=False` because its API key already authenticates the caller.
- DO keep new API responses in matching `schemas/` file.
- DON'T edit `build_digest` or `render_digest_html` to add a report or analytics field: V4's `trend`/`funnel`/`top_questions` are a separate additive read over the same window precisely so the digest payload and HTML stay byte-identical (V4 invariant 15, re-checked at gate `V4-1G` against the module from tag `v3`); per-conversation insights (F2) must follow the same rule.
- DON'T add dependencies without need — `pyproject.toml` / `frontend/package.json` already cover LLM providers, mail, redis, antd.
- DON'T tighten CORS or rename env keys without updating `.env.example`, `README.md`, and `frontend/.env*`.
- DON'T break widget backward compat (`ChatWidgetConfig` keys, `localStorage` session/history keys).
- DON'T move, delete or force-push a published release tag (`git tag -f`, `git push -f origin <tag>`): it is cut **once**, on the exact commit the gate verified, and stays there — `v3` is `2e5ab73` even though docs kept landing after it. Anything that belongs in a tagged release is committed **before** tagging (the gate commit carries the plan/README/AGENTS updates); docs written afterwards live on `master` and stay untagged. A mistake already inside a tag is fixed with a new tag (`v3.0.1`), never by rewriting the old one. Full policy: `plans/PLAN_V3.md` §8 "Release tags are immutable".

## Trail — repo context graph

This repo is indexed in `.trail/cache/`: small linked markdown nodes that explain each
system and carry exact file:line spans, kept in sync with the code through git.

For ANY task here — understanding how something works, finding where code lives,
or scoping a change — get context from the graph before grepping or opening
source files. Re-ask freely (it's cheap) and reuse literal identifiers you
already have (symbol, error string, file name) as the query. New to this repo?
Run `trail map` first — a token-budgeted orientation (dir clusters, hubs,
hotspots), no LLM, no key.

- Run `trail ask "<your question>" --source` → ranked nodes with the relevant
  code spans inlined (each hit's ≤8-line crux by default; `--full` for whole
  definitions when the crux isn't enough). Match the tool to the task shape:
  for understanding or editing, the top node IS the answer — cite its
  `covers:` file:line spans and edit straight from `--source`. For
  exhaustive tasks ("every occurrence / every caller of this pattern"), ranked
  results are top-N, not complete — run `trail grep "<literal>"` instead
  (exhaustive over indexed files, grouped by enclosing symbol), falling back
  to raw `grep -rn` only for unindexed files.
- `trail skeleton <file>` → every definition's signature + span, ~10× cheaper
  than reading the file; use it to skim an API surface.
- `trail callers <symbol>` gives precomputed, exact edges — who calls this.
  Add `--direction out` for what it calls, or `--depth N` to walk
  transitively for the full blast radius. For structural questions, skip
  ranking and use this directly.
- Or browse: `.trail/cache/INDEX.md` lists every node; follow the links.
- Monorepos and folders of multiple repos rank fairly across sub-projects —
  hits carry `[scope/]` labels naming which one they're from. Narrow with
  `trail ask "<task>" --in <scope>/` once you know where you're working.

If a returned span is truncated ("+N more lines"), open the file at that exact
range before finalizing. Only open source files when a node genuinely lacks a
needed detail, and then at the exact file:line the node points to — never
re-read whole files.

After big code changes, refresh the graph with `trail build` (deterministic,
no API key, $0).
